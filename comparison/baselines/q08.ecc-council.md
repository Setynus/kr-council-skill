## Council: 모바일 앱 React Native vs 네이티브 2벌

**Architect:** React Native(Expo 개발 빌드)로 가되, 카메라·위치 핵심 시나리오를 초기에 실기기로 검증한 뒤 확정합니다.
인력(웹 프론트 2명 + 안드로이드 1명, iOS 0명)과 6개월 일정에서 코드베이스 두 벌은 감당하기 어렵고, 막히는 지점만 네이티브 모듈로 내려가는 편이 유지보수에 유리합니다.

**Skeptic:** "RN이냐 네이티브냐"는 거짓 이분법이며, 진짜 질문은 "카메라·위치가 RN 기성 모듈(vision-camera, expo-location)로 충분한가"입니다. 첫 주 스파이크로 검증하면 논쟁이 끝납니다.
진짜 병목은 프레임워크가 아니라 iOS 경험자 0명과 스토어 심사이므로 iOS 빌드/TestFlight 파이프라인을 1개월 차에 먼저 돌려야 합니다.

**Pragmatist:** React Native(Expo + 개발 빌드)로 한 번에 갑니다. 웹 프론트 2명이 바로 생산성을 내고 네이티브 2벌은 일정상 불가능합니다.
병목은 개발 속도보다 iOS 백그라운드 위치 심사·권한 문구·스토어 심사이므로 심사 버퍼를 최소 3~4주 잡고, 안드로이드 담당자를 네이티브 이슈 전담으로 고정합니다.

**Critic:** RN을 추천하되 "한 번에 둘 다 끝난다"는 낙관은 버리고 2주 안에 실기기 프로토타입으로 검증해야 합니다. 카메라·위치가 핵심이라는 점이 RN의 가장 약한 영역입니다.
실시간 프레임 처리·백그라운드 위치·기기별 카메라 파편화에서 한계에 부딪히면 iOS 네이티브 모듈을 짤 사람이 없어 일정이 한 번에 무너지며, 요구사항에 따라 결론이 네이티브 쪽으로 뒤집힐 수 있습니다.

### Verdict
- **Consensus:** 네 입장 모두 React Native(Expo 개발 빌드) 선택에 수렴하며, 네이티브 2벌은 3명·6개월·iOS 경험자 0명 조건에서 비현실적이라고 봅니다. 또한 초기 실기기 스파이크와 iOS 배포/심사가 실제 병목이라는 점도 일치합니다.
- **Strongest dissent:** Critic의 경고입니다. 백그라운드 위치나 실시간 프레임 처리가 핵심 요구라면 RN이 한계에 부딪히고 iOS 네이티브 인력 공백이 치명적이어서 결론이 뒤집힐 수 있습니다. 이 우려는 기각하지 않고 스파이크의 통과 기준으로 반영합니다.
- **Premise check:** Skeptic이 질문 자체를 도전했습니다. "RN 대 네이티브"가 아니라 "카메라·위치 요구가 RN 기성 모듈로 충족되는가"와 "iOS 경험자 0명 문제"가 본질이라는 지적이며, 타당하다고 판단합니다.
- **Recommendation:** React Native(Expo 개발 빌드)로 진행합니다. 1~2주 안에 카메라·위치 핵심 시나리오를 iOS/안드로이드 실기기(저가형 포함)에서 스파이크로 검증하고, 통과 시 확정합니다. 1~2개월 차까지 TestFlight와 Play 내부 테스트 배포 파이프라인을 먼저 구축하며, 스토어 심사 버퍼 3~4주를 확보하고 안드로이드 경험자를 네이티브 모듈 전담으로 둡니다. 스파이크에서 백그라운드 위치·실시간 프레임 처리가 RN으로 불가능하다고 확인되면 해당 기능만 네이티브 모듈로 분리하거나 접근을 재검토합니다.
