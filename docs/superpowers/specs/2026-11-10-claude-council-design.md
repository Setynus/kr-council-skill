# claude-council 설계 문서 (개정 2: 공식 스킬 가이드 반영)

- 작성일: 2026-11-10 / 개정 2: 2026-11-10
- 상태: **승인됨**. 단, 원격 저장소 생성·푸시는 생성 직전 별도 확인(§9)
- 규모: 프로젝트(전체 설계)
- 개정 이유: Anthropic 공식 문서·가이드 PDF·설치된 `skill-creator` 지침을 조사해 이름 규칙, 폴더 구조, 경로 처리, 평가 방식을 바로잡았다(§11 출처).

## 1. 의도와 이유

한국어 사용자가 어려운 결정을 내릴 때, 한 번의 답변 대신 서로 다른 관점의 위원 5명과 위원장의 판정을 받는 Claude 스킬을 만든다.

- 사용자: 본인 한 명. 비공개 GitHub 저장소 `Setynus/claude-council`에서 관리한다.
- 영감: Karpathy의 llm-council 방법론(MIT)과 `aiwithremy/claude-skills-llm-council`. 원본은 라이선스가 없으므로 **문장을 옮기지 않고 같은 방법론으로 처음부터 새로 쓴다.**
- 기존 `ecc:council`, `ecc:council-multi-model`은 영어권 기준이다. 한국어 트리거·출력, 한국 제도·시장 맥락, 시각적 보고서가 빠져 있다.

### 1.1 이름 (사용자에게 알린 내 판단)

- **저장소 이름: `claude-council`** (사용자 지정, 그대로 유지).
- **스킬 이름(`name`)·스킬 폴더 이름: `council-kr`.** 공식 문서가 스킬 `name`에 `claude`, `anthropic`을 쓰지 못하게 하고("Cannot contain reserved words"), 폴더 이름은 `name`과 같은 kebab-case여야 한다. 사용자의 기존 `canvas-design-kr` 이름 규칙과도 맞는다. 사용자가 입력하는 명령은 `/council-kr`이다.
- 다른 스킬과 이름이 같지 않다: `ecc:council`, `ecc:council-multi-model`과 구분된다.

## 2. 목표 / 비목표 / 반목표

**목표**
1. 한국어로 호출하고 한국어로 답하는 의회형 의사결정 스킬
2. 결과물은 자체 완결형 **HTML 대시보드**: 위원 5명의 판단 카드, 상호 검토 결과, 위원장 최종 검토 보고서
3. 5명 **동시(병렬) 생성**과 독립성이 구조로 보장될 것(핵심 요건, §5)
4. ecc 스킬이 삭제된 뒤에도 재현 가능한 비교 평가와, skill-creator 방식의 스킬 자체 평가(§7)
5. 공식 가이드의 구조·이름·설명 규칙을 자동 검사로 지킨다(§6.5)

**비목표**
- 코드 리뷰, 구현 계획, 사실 조회, 요약, 글쓰기(의사결정이 아닌 작업)
- 서로 다른 AI 회사 모델 호출(교차 모델). 1차 범위 밖
- 웹 서버·DB·자동 점수 대시보드, Claude API 직접 호출

**반목표(기능해도 실패)**
- 같은 모델이 낸 5개 의견을 "독립된 5명의 전문가 의견"처럼 과장
- 소수 반대 의견을 판정에서 지움
- 번역투 한국어, 한글이 깨지는 보고서
- 사소한 질문에도 하위 호출 11개 비용을 씀

## 5. 핵심 요건: 동시 생성과 독립성

사용자가 핵심으로 지정한 원칙을 "희망"이 아니라 "메커니즘"으로 명시하고 **실측으로 검증**한다.

1. 5명 자문 호출은 **한 번의 응답에 한 묶음**으로 낸다. 5명 상호 검토 호출도 같다. (공식 Claude Code 문서는 이 묶음 방식을 직접 설명하지 않고 "여러 하위 에이전트를 동시에 띄운다"고만 한다. 묶음 지시는 비용이 없어 유지하되, 효과는 아래 6번으로 실측한다.)
2. 하위 에이전트는 새 컨텍스트의 `general-purpose` 유형으로 **명시**하고, 대화 전체를 물려받는 **`fork`는 금지**한다. (`context: fork` frontmatter도 쓰지 않는다.)
3. 각 호출에는 **구성된 질문과 필요한 맥락만** 준다. 다른 위원의 답과 대화 이력은 주지 않는다. 이것이 앵커링을 막는 실질 장치다.
4. 5개 호출을 모두 낸 **뒤에** 결과를 읽는다. 상호 검토는 5개가 모두 끝난 뒤에만 시작한다.
5. 실행 전에 하위 호출이 11개(5+5+1)라는 점을 알리고 사용자 동의를 받는다.
6. **검증(`tools/check_parallel.py`)**: 대화 기록에서 (a) 한 응답에 Agent 호출 5개 묶음, (b) 5개 모두 시작된 뒤에 첫 결과를 읽음, (c) 위원 프롬프트에 다른 위원의 출력이 없음, (d) `fork` 미사용을 확인한다. 동시 실행 상한(문서상 약 20개)을 넘지 않게 평가 실행은 한 번에 한 건씩 한다.
7. 하네스의 "요청 없이 하위 에이전트를 만들지 말라"는 기본 규칙에 막히지 않도록, SKILL.md가 소집을 명시적 지시로 쓴다.

### 5.1 실행 방식 3단계와 자동 선택 (다른 플랫폼 대응)

"세션 5개 생성"은 정확한 표현이 아니다. Claude Code에서 일어나는 일은 메인 대화 안에서 하위 에이전트를 동시에 호출하는 것이다. 스킬이 새 세션을 열 수는 없다.

| 방식 | 환경 | 동작 | 독립성 |
|---|---|---|---|
| 병렬 | Agent 도구가 있는 곳(Claude Code CLI·데스크톱) | §5 규칙대로 5+5+1 호출 | 높음 |
| 프롬프트 묶음(수동) | 하위 에이전트 없음 + 사용자가 진짜 독립을 원함 | 5명용 프롬프트 5개를 생성, 사용자가 새 대화 5개에 붙여넣고 결과 JSON을 가져옴 | 높음(수고 큼) |
| 단일 세션 | 그 외 | 한 대화에서 5명을 차례로 작성 | 낮음 |

- 시작 시 "Agent 도구가 보이는가"로 방식을 고르고 **보고서 상단에 실행 방식을 표기**한다.
- 단일 세션은 "앞 위원의 답이 뒤 위원에 영향을 줄 수 있음"을 명시하고 신뢰도를 낮춰 표기한다. 지키지 않는 규칙을 지키는 척하지 않는다.
- 근거(출처 있음): skill-creator의 claude.ai 안내는 "Claude.ai doesn't have subagents"라고 한다. 공식 문서는 스킬이 "code execution environment with filesystem access, bash commands"에서 돈다고 하고, claude.ai는 npm·PyPI 패키지 설치가 가능하다고 한다. 개발 환경에서의 실측은 구현 단계(Task 8)에서 확인하며, 실측 전에는 "문서상"으로만 적는다.
- 렌더러는 코드 실행이 되는 환경에서만 동작한다. 그렇지 않으면 HTML을 대화에 직접 출력하는 대안 경로를 둔다.
- `compatibility` frontmatter에 "Claude Code(병렬), claude.ai(프롬프트 묶음/단일 세션), Python 3 필요"를 적는다.

## 6. 설계

### 6.1 저장소 구조

공식 가이드 규칙: 스킬 폴더 이름은 `name`과 같은 kebab-case, 파일은 정확히 `SKILL.md`, **스킬 폴더 안에 README.md 금지**. 그래서 배포되는 스킬 폴더와 개발용 파일을 나눈다.

```
claude-council/                      # 저장소 루트(비공개 GitHub)
  README.md  NOTICE.md  .gitignore
  council-kr/                        # ← 스킬 폴더(배포·설치 대상, README 없음)
    SKILL.md
    scripts/render_report.py         # JSON → HTML, A~E 셔플
    assets/report.html               # 대시보드 템플릿(CDN 없음)
    references/advisors.md           # 5명 관점(한국어로 새로 작성)
    references/ko-context.md         # 한국 맥락 체크리스트
    evals/<케이스>/                  # skill-creator 형식 테스트(§7.1)
  tests/                             # unittest (렌더러, SKILL.md 규칙 검사, 도구)
  tools/check_parallel.py            # 동시 호출 검사(개발 전용)
  tools/blind_pack.py                # 블라인드 채점 묶음(개발 전용)
  comparison/                        # 교차 비교 평가: 질문, 루브릭, 동결 기준선, 결과(§7.2)
  council-kr-workspace/              # skill-creator 실행 결과(gitignore)
  docs/superpowers/specs|plans/
```

- 설치: `~/.claude/skills/council-kr` → `<저장소 루트>\council-kr` 심볼릭 링크.
- 배포(claude.ai 업로드용): `council-kr/` 폴더를 zip으로 압축(skill-creator의 `package_skill.py`).

### 6.2 실행 흐름
1. **프레이밍**: 질문과 맥락을 짧게 읽어 중립적인 질문문으로 정리. 모호하면 되묻기 1회. 비용 고지·동의.
2. **자문 소집**: 5명 동시 호출. 응답은 정해진 JSON(입장, 근거 3개, 위험, 놓치기 쉬운 점).
3. **상호 검토**: 스크립트가 A~E 매핑을 `random.shuffle`로 만들어 저장(LLM은 난수를 만들지 않는다). 5명이 익명 응답을 보고 가장 강한 것·가장 큰 사각지대·모두가 놓친 것을 답한다. 동시 호출.
4. **위원장 종합**: 매핑을 풀어 실명으로 읽고 판정 JSON 작성: 합의, 충돌(소수 의견 보존), 사각지대, 권고, 단 하나의 첫 행동.
5. **렌더링**: `python "${CLAUDE_SKILL_DIR}/scripts/render_report.py" render ...`. 저장 경로는 작업 폴더의 `council-reports/`.

스크립트 경로는 사용자의 작업 폴더가 아니라 스킬 폴더 기준이어야 하므로 `${CLAUDE_SKILL_DIR}`(슬래시 `/` 사용)를 쓰고, 치환되지 않는 환경을 위해 "이 SKILL.md가 있는 폴더"라는 대체 문구를 함께 둔다.

### 6.3 정직성 표기
- 보고서 상단에 "같은 모델이 서로 다른 관점으로 낸 의견이며, 독립된 전문가 5인이 아닙니다." 고정 표기.
- 위원장 보고서에 "신뢰도"와 "소수 의견 유지 여부" 표기.

### 6.4 한국화
- 트리거는 다른 스킬과 충돌하지 않는 고유 문구: "위원회 열어줘", "자문단 소집", "council 돌려줘". "검토해줘" 같은 일반 문구는 쓰지 않는다.
- `ko-context.md`: 원화·세금·4대 보험, 개인정보보호법·근로기준법 등 제도, 스마트스토어·카카오·네이버 등 플랫폼, 위계·관계·체면 문화, 자문 비용 현실.
- 용어는 **"위원"** 하나로 통일한다(자문관 등 혼용 금지). 문체는 질문자의 존댓말을 따르고, 보고서는 정중한 평서문. 번역투 금지.

### 6.5 SKILL.md 작성 규칙 (공식 가이드, 자동 검사 대상)
- `name`: kebab-case, 64자 이하, 폴더 이름과 동일, `claude`·`anthropic` 미포함.
- `description`: 1,024자 이하, `<` `>` 없음, 3인칭 현재형("…한다"), **무엇을 + 언제**, 사용자가 실제로 쓰는 표현, **"쓰지 않는 경우" 문장**, 약간 적극적으로(언더트리거 방지).
- 본문 500줄 미만(5,000단어 미만). 참조 파일은 SKILL.md에서 **한 단계 깊이**만, 100줄이 넘으면 목차. 경로는 슬래시 `/`.
- **중요 지시(병렬·독립 규칙, 비용 동의)를 본문 맨 위 `## 중요`에** 둔다.
- 스크립트는 "실행하라"와 "참고하라"를 구분해 쓰고, 오류는 스크립트가 구체적 메시지로 직접 처리(Claude에게 떠넘기지 않음). 결정적 검증은 스크립트가 맡는다.
- 옵션을 나열하지 않고 기본값 하나를 제시한다. 시간이 지나면 낡는 정보는 넣지 않는다.
- 이유를 설명하는 서술을 쓰고, 대문자식 강한 명령은 피한다(skill-creator 지침).

## 7. 평가 (두 체계, ecc 삭제 가능성 반영)

### 7.1 스킬 자체 평가 — skill-creator 방식
- 원칙: **평가를 SKILL.md보다 먼저** 만든다(공식: "Create evaluations BEFORE writing extensive documentation").
- 기능 케이스 3개를 `council-kr/evals/<케이스>/`(`prompt.md`, `case.yaml`, `graders/NN-*.md`)에 쓴다: 가격 결정 질문에 위원회가 열림 / 사소한 사실 질문에는 열리지 않음 / 보고서에 카드 5개·실행 방식 표기가 있음.
- 트리거 질의 약 20개(소집해야 하는 것 8~10, **근접 오답** 8~10: "검토해줘", 문서 검수 등)를 `tests/trigger-eval.json`에 둔다.
- 실행: `with_skill` 대 `without_skill`을 `council-kr-workspace/iteration-N/`에서 **한 번에 한 건씩** 실행(병렬 상한 보호). 채점 `grading.json`(`text/passed/evidence`), 집계 `benchmark.json`, 그리고 **`generate_review.py` 뷰어로 사용자 검토를 받는 정지 지점**을 둔다.
- Haiku·Sonnet·Opus 모델별로 케이스 1개씩 구조 통과/실패만 확인한다(공식 체크리스트).
- 비용이 드는 단계(설명 최적화 `run_loop.py`, `claude plugin eval`)는 실행 전에 사용자에게 제안하고 승인받는다.

### 7.2 교차 비교 — ecc 삭제 후에도 재현
평가가 ecc의 설치 여부에 의존하지 않도록, 설치돼 있는 지금 기준선을 한 번만 확보해 `comparison/`에 얼린다.
1. 질문 10개를 `comparison/questions.md`에 고정(사업·진로·개발·개인 재무, 한국 맥락 필요 6개 이상).
2. 기준선 시스템:
   - `ecc-council`: 10개 질문 모두.
   - `single`(단일 답변): 10개 모두.
   - `orig-method`(원본 방식, 약 11호출/질문): **3개 질문만**(비용 때문).
   - `ecc-council-multi-model`: **`codex` CLI가 설치돼 있지 않아 확보 불가.** 해당 스킬 규칙대로 "external review absent"로 기록한다. 그 스킬의 council 부분은 `ecc-council`과 같다. (설치돼 있더라도 질문을 OpenAI로 보내려면 사용자 동의가 필요하다.)
3. ecc 버전/커밋을 기록하고 라이선스를 확인한 뒤 **출력만** 보관한다(스킬 본문은 복사하지 않는다).
4. **블라인드 채점**: 채점 하위 에이전트가 이름을 가린 무작위 순서의 결과를 루브릭(한국어 자연스러움, 한국 맥락, 구체적 권고, 반대 의견 보존, 첫 행동 하나)으로 채점. 구조 검사(JSON 유효, 카드 5개, 한글 깨짐 없음, 동시 호출, `fork` 미사용, 실행 방식 표기)는 통과/실패로 분리.
5. 한계를 결과 문서에 적는다(같은 모델이 채점, 질문 10개, `orig-method`는 3개).

## 8. 제약

- 원본 저장소의 문장·프롬프트 템플릿을 옮기지 않는다.

- 상위 작업 폴더에는 `git init`하지 않고 이 저장소 폴더에서만 한다.
