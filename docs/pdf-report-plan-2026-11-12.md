# 위원장 최종 보고서 PDF(A4 가로) 전환 계획

- 작성일: 2026-11-12 (계획만 수립, 코드 변경 없음)
- 대상: `kr-council-skill` v0.2.2 → 다음 버전 후보 0.3.0
- 용도: 다음 세션 시작 시 이 문서를 읽고 바로 구현에 들어간다.

## 1. 확정된 요구사항 (사용자 결정)

1. 최종 보고서 출력물을 **A4 용지 가로(297 × 210 mm) 인쇄용 PDF**로 바꾼다.
2. 앞서 검토한 "Claude Design용 브리프"의 필수 요소는 PDF 페이지 구성·배치에 반영한다.
3. 탭·스크롤·반응형 같은 화면 전용 요소는 쓰지 않는다(인쇄물이 기준).

## 2. 현황 (확인한 사실)

| 항목 | 내용 | 확인 방법 |
|:--|:--|:--|
| 렌더러 | `kr-council-skill/scripts/render_report.py` 234줄, 표준 라이브러리만 사용(argparse, html, json, random, re, sys, pathlib) | 파일 import 목록 |
| 서브커맨드 | `shuffle`(익명 매핑), `render`(JSON → HTML, 검증 실패 시 종료 코드 2) | `SKILL.md` 3·5단계 |

| 이 샌드박스 | reportlab 설치됨, weasyprint 미설치, 한글 글꼴은 WenQuanYi Zen Hei만 확인 | 실행 결과 |

미확인: 사용자 PC의 OS, Python 버전, 설치된 PDF 라이브러리, 한글 글꼴. 다음 세션 첫 단계에서 확인한다.

핵심 충돌: 현재 `SKILL.md`의 `compatibility`는 "Python 3만 필요"인데, PDF 생성은 외부 도구가 필요하다. 이 충돌을 해소하는 방식이 이번 계획의 첫 번째 결정 사항이다.

## 3. 다음 세션 첫 단계에서 사용자에게 확인할 결정 3가지

### 결정 1. PDF 생성 방식

| 방식 | 장점 | 단점 | 적용 조건 |
|:--|:--|:--|:--|
| A. reportlab(순수 Python) | 설치가 쉽다(`pip install reportlab`), 브라우저·시스템 라이브러리 불필요, 페이지 크기·분할을 코드로 정확히 제어 | 레이아웃을 코드로 직접 그려야 해서 작업량이 크고, 한글 TTF 임베딩을 직접 처리해야 한다 | 사용자 PC에 pip 설치가 가능할 때 |
| B. HTML 생성 + 헤드리스 Chromium 인쇄 | 기존 HTML/CSS 렌더러를 재사용, `@page { size: A4 landscape }`로 간단히 제어, 한글 렌더링이 안정적 | Chromium 설치 필요, 환경마다 실행 경로가 다르다 | Chrome/Edge가 있는 PC |
| C. HTML 유지 + 인쇄 CSS만 추가 | 의존성 0, 구현이 가장 작다 | PDF 저장은 사용자가 브라우저에서 직접 해야 하므로 "PDF 출력"이 자동이 아니다 | 자동화보다 단순함이 우선일 때 |

권장: 방식 B를 기본으로 하고, Chromium이 없으면 방식 C로 폴백한다. 이유는 한글 글꼴·줄바꿈·표 분할을 브라우저가 가장 안정적으로 처리하고 기존 렌더러의 검증 로직을 그대로 쓸 수 있기 때문이다. 단 사용자 PC에 Chrome 또는 Edge가 있는지 확인이 필요하다. 없으면 방식 A로 전환한다.

### 결정 2. 기존 HTML 출력 유지 여부

- 유지: 하위 호환과 화면 미리보기 가능, 코드 양 증가.
- 삭제: 구조 단순, 기존 평가(`evals`)·테스트·문서를 모두 고쳐야 함.
- 권장: 중간 산출물로 HTML을 유지하되 최종 결과물은 PDF로 안내한다(방식 B와 자연스럽게 맞는다).

### 결정 3. 한글 글꼴

- 시스템 글꼴 의존(맑은 고딕, Apple SD Gothic Neo 등): 용량 증가 없음, 환경별 모양 차이.
- 글꼴 파일 번들(Pretendard 또는 Noto Sans KR, 라이선스 확인 필요): 모양이 일정, 저장소 용량 증가.
- 권장: 시스템 글꼴 우선 + 글꼴 없음 감지 시 경고. 번들은 라이선스 확인 후 선택한다(미확인).

## 4. PDF 페이지 구성안 (A4 가로, 여백 12~15mm)

Design 브리프의 필수 요소를 매핑한다.

| 쪽 | 구성 | 브리프 출처 |
|:-:|:--|:--|
| 1 | 헤더(제목, 정리된 질문, 작성 시각, 실행 방식 배지) + 한계 고지 띠 + **권고(한 문장)** + **가장 먼저 할 한 가지** + 신뢰도 배지(높음·보통·낮음) + 소수 의견 반영 배지(true일 때만) | 탭 밖 고정 영역 |
| 2 | 위원장(파파스머프) 판정 상세: 합의된 점, 충돌 지점(쟁점 / 입장 2열), 놓친 점 | 최종 판정 탭 |
| 3 | 위원 카드 5장(호칭, 입장, 근거 3개, 위험, 사각지대). 같은 크기·같은 위계. 한 쪽에 3장 + 다음 쪽에 2장 또는 5장 축소 배치를 시안으로 비교 | 위원 5인 탭 |
| 4 | (카드 나머지) | |
| 마지막 | 익명 상호 검토 표(검토자 / 가장 강한 응답 / 가장 약한 응답 / 모두가 놓친 것) + A~E 실제 위원 매핑 | 상호 검토 탭 |

공통 규칙:
- **한계 고지**("같은 모델이 서로 다른 관점으로 낸 의견이며, 독립된 전문가 5인이 아닙니다.")는 모든 쪽 하단에 반복 표기하고 쪽 번호(n / N)를 함께 쓴다.
- 신뢰도·소수 의견 배지는 흑백 인쇄에서도 구분되도록 **색 + 텍스트를 병기**한다.
- 카드·표 행은 쪽 중간에서 끊기지 않게 한다(`page-break-inside: avoid` 또는 reportlab `KeepTogether`).
- 본문 최소 9~10pt(인쇄 가독성, 추정 기준)로 하고, 5열 축소 배치는 이 기준에서 오버플로가 나는지 실측해 결정한다.
- 위원 응답이 최대 300단어(`SKILL.md` 2단계)이므로 최대 길이 입력으로 오버플로 시험을 한다.
- 위원 간 우열을 암시하는 색·순서를 쓰지 않는다.

## 6. 작업 순서 (테스트 우선)

1. 환경 확인과 위 결정 3가지 확정(사용자 질문).
2. 실패하는 테스트를 먼저 작성: PDF 생성, 쪽 크기 842 × 595pt(A4 가로), 쪽 수 ≥ 3, 한글 텍스트 추출 가능.
3. 렌더러 구현: 1쪽 → 2쪽 → 위원 카드 → 검토 표 순으로 쌓는다.
4. 최대 길이 입력과 최소 입력(위원 근거 3개만)으로 레이아웃 시험.
5. `SKILL.md`, `evals`, 문서 갱신 후 전체 테스트 실행.
6. 육안 검토: PDF를 이미지로 변환해 쪽별로 확인(한글 깨짐, 잘림, 빈 쪽).
7. 버전·변경 이력 갱신, 커밋과 PR(사용자 요청 시).

## 7. 성공 판정 기준 (검증 방법)

- `python scripts/render_report.py render <json> --out <file>.pdf` 종료 코드 0.
- PDF 쪽 크기가 모두 842 × 595pt(±1pt): `pypdf` 또는 `pdfinfo`로 확인.
- `pdffonts`로 한글 글꼴이 **임베딩**되어 있음 확인(미임베딩이면 다른 PC에서 깨질 수 있다).
- `pdftotext`로 한계 고지 문구, 신뢰도, 권고 문장이 그대로 추출됨.
- 흑백 변환 후에도 신뢰도·소수 의견 배지가 글자로 구분됨.
- 기존 테스트 전체 통과, 새 테스트 통과.
- 잘못된 JSON 입력은 종료 코드 2와 필드별 오류 메시지를 유지(기존 동작 회귀 없음).
